Two things changed the shape of the corpus this pass. First, local-only skills stopped being invisible: skills that live in an install root but not in the vault are now either adopted (copied in, made the source of truth, registered) or declared external (owned upstream, tracked with a verify command). Second, the catalogs became derived: the manifest and README counts are generated and checked, so an imported skill cannot become an orphan by forgetfulness.

The entity system itself did not change. What changed is that the system now has an operational edge: a decision test for ownership, an importer that enforces the gates, and an installed-copy guard (Talos) that can tell the difference between "behind", "forked", "furniture", and "never installed here".

The one sentence. The vault is the copy of record; every machine's install root is a projection of it; Talos proves the projection; anything the projection has that the vault does not is either adopted, declared external, or allowlisted as a deliberate machine-local fork.

02 — Ownership

Every installed skill falls into exactly one bucket.

The bucket is decided by one question: would a copy in the vault be wrong within one upgrade? If yes, it is external. If no and it is ours, it is owned. If it is ours but this machine intentionally carries a different copy, it is a machine exception.

BucketTestOperationGuard
Owned We author it, or it is a durable local artifact (knowledge pack, SOP, script) Adopt into skills/<category>/ Talos ok
External Content is generated or shipped by a package we install (Orca, Omarchy, skills.sh) Declare in registries/_externals.md, never vendor Talos external
Machine exception Ours, but this machine deliberately holds a full or forked copy List in ~/.config/agent-vault/talos-allowlist.txt Talos allowed

Why externals are not vendored

Orca's orca-cli, orchestration, and computer-use are discovery stubs. They fetch a version-matched guide from the running binary (ORCA skills get <name>), so a vault copy would pin prose to the wrong build. Omarchy's omarchy and diagnose-crash are symlinked out of /usr/share/omarchy and updated by the OS. find-skills exists to drive npx skills, the package manager that already owns it. The registry stores owner, install path, and a re-runnable verify command for each.

What "adopt" means mechanically

vault-import.sh refuses symlinks and declared externals, validates that the frontmatter name matches the directory and the description is long enough to route on, scans for secrets and other users' absolute home paths, copies with .git and node_modules excluded, and then refreshes the live copy from the vault. The vault is the source of truth from that moment, not the machine.

03 — The entity system

An entity is a file that changes behavior at the moment of use.

Five conditions make something an entity rather than a draft: a unique kebab-case identity matching its directory; a routing contract (the description); a body (procedure, lens, or procedure with examples); exactly one home scope; and one registry line. The full reference is the taxonomy site.

05 — Talos

The installed-copy guard: prove the projection, never guess.

vault-audit.py --installed compares every vault skill against every install root by content hash. It is named for the bronze automaton that patrolled Crete: it walks the perimeter, states what it finds, and does not repair what it cannot understand.

StatusMeaningAction
okInstalled copy is byte-identical to the vaultnone
linkedSymlink resolves to content identical to the vaultnone
repairedCopy was replaced or installed during this runnone
driftCopy exists and differs; no extra files. The vault moved on--repair
divergedCopy holds files the vault does not — a fork or fuller checkouthuman; --force only if intended
allowedDivergence declared deliberate in the machine allowlistnone; keep the list short
externalInstalled and declared package-managed in _externals.mdnone; verify upstream
missingNot installed on this machineA choice, not an error; install on demand
unmanagedInstalled, not in the vault, not declared externaladopt or declare

Rules it will not break

  • It never guesses: a name containing a path separator is refused, so a repair cannot write outside the install root.
  • It never deletes a superset: a copy with extra files is diverged, not stale, and --repair leaves it alone without --force.
  • It never repairs an allowlisted fork: the allowlist is checked before repair.
  • It is read-only by contract in every mode except an explicit --repair*.

Roots default to ~/.agents/skills and ~/.pi/agent/skills, overridable with --install-roots or $PI_SKILLS_DIRS. Nested layouts are found too: a skill may live flat (<root>/<name>) or inside a category folder (<root>/<category>/<name>).

The two roots are not symmetrical on purpose: this machine installs the corpus into ~/.agents/skills and lets ~/.pi/agent/skills hold only the package symlinks and the pattern registries. missing at the second root is the honest description of that policy.

06 — Migration across machines

The vault is the source; each machine is a projection with a receipt.

A skill moves in one direction: author or adopt on the machine where it is edited, push to GitHub, pull on every other machine, then let Talos prove the install. The install root is never edited in place as the copy of record.

Runbook

  1. Author here. Create skills/<category>/<name>/SKILL.md, then vault-manifest.sh --write, vault-audit.py --short, and push.
  2. Adopt something already installed. vault-import.sh <name> --category <cat> runs the gates, copies, and refreshes the live copy from the vault.
  3. Declare upstream furniture. Add a row to registries/_externals.md with owner, install path, and a re-runnable verify command. Never import it.
  4. Pull everywhere else. PI_SKILLS_DIR=~/.agents/skills ./scripts/vault-sync.sh --install, then python3 scripts/vault-audit.py --installed.
  5. Before every push. ./scripts/vault-manifest.sh --check && python3 scripts/vault-audit.py --short.

Why the other machine is read over SSHFS. Project-scoped grounding (the bilan packaging tree, the live site repo) lives on manjaro-inspiron7548. This machine mounts its home at ~/remote-manjaro read/write, so verification can read the real files instead of trusting a summary. The mount is a reference, not an install root — nothing in the vault is written there except through git.

07 — Health and the four fixes

Eight states. Four findings closed. Two were never real.

zombie

Fails to load — bad YAML, missing description, name ≠ directory.

ghost

Something references an entity that does not exist.

duplicate

Two entities with ≥85% description overlap. Merge or sharpen.

orphan

Exists but no registry or catalog lists it.

hollow

No procedure, no references, no examples. Costs context, returns nothing.

stale

Dated grounding past the threshold. Explicit Last verified: wins; fenced examples and audit-history tables are records, not grounding.

statue

Never invoked. Usually the trigger's fault, not the body's.

drift

Upstream moved. Loadable, consistent, confidently wrong. Test with a probe.
